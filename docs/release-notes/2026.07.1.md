# shard-db 2026.07.1

kf-corruption recovery (`rebuild-kf`) and an `add-index`/`remove-index` locking fix that could corrupt index files under concurrent writes. **Operators who ran `vacuum`/compact on a 2026.06.4 install, or who rebuild indexes (`add-index`/`remove-index`) under concurrent write load, should run `./migrate` after upgrading** to repair any accumulated kf corruption. Wire-compatible with 2026.06.4 — no client changes needed.

## Highlights

- **`rebuild-kf` recovery command** — repairs corrupted/dangling kf (keyfile) entries by rescanning every segment file and re-deriving each live record's kf slot from scratch. Fixes the root cause: a `vacuum`/compact guard bug that could delete a donor segment file even when the kf entry pointing to it failed to update, leaving records unreachable by key lookup despite still existing on disk.
- **`add-index`/`remove-index` exclusive locking** — both commands now take the exclusive per-object lock (`objlock_wrlock`), closing a race where a concurrent insert's on-the-fly index update could land on the same index file mid-rebuild and either get silently discarded or corrupt the B-tree pages being written. Root cause of a production trigram-search undercount that worsened the longer a rebuild ran (multi-field rebuilds were more exposed than single-field ones).
- **`rebuild_object_v2` (vacuum --splits) recovery** — a walk failure during a splits-changing rebuild no longer strands the object in a half-migrated state; the original `data/` is restored automatically. A single corrupt record during the walk is now skipped (logged, not fatal) instead of aborting the entire rebuild.
- Several correctness/segfault fixes surfaced while building the above (see Fixes).

## kf corruption recovery

### Root cause

`cmd_vacuum`'s light path (`slotcask_compact_segs` → `compact_one_stream_varlen`, introduced in 2026.06.4's variable-length records work) merges sparse donor segment files into denser recipients, then deletes the donor. `compact_migrate_records_varlen` returned success even when a record's kf update was silently skipped — including when `kf_lookup_with_slot` failed because the segment file the kf entry currently pointed at was already missing or corrupted. The kf entry still referenced the donor file, but the donor got deleted anyway, leaving a dangling pointer. Symptom: records intermittently unreachable by key despite existing on disk; bulk-insert paths that need `pre_commit_needs_old=1` (triggered by any btree index) failing with `some_records_dropped`.

### The fix

- **compact-kf guard** — the donor file is no longer deleted if any record's kf update couldn't be confirmed during migration.
- **`rebuild-kf`** — new command that repairs already-corrupted kf entries by rescanning all segment files for an object and rebuilding kf slots from what's actually on disk.

```json
{"mode":"rebuild-kf","dir":"<dir>","object":"<obj>"}
```

```bash
./shard-db rebuild-kf <dir> <obj>
```

Idempotent — a clean object reports `{"status":"ok","repaired":0}`.

### Automatic repair

- **`./migrate`** runs `rebuild-kf` automatically (phase 2/3, before compact) on every upgrade, and writes a `.kf_rebuild_done` sentinel so it isn't repeated on every subsequent embedded startup.
- **Embedded (npm) clients** auto-run `rebuild-kf` once per `db_root` on first use, gated by the same sentinel — npm users get the repair with zero manual steps. Also exposed directly as `shardDb.rebuildKf(dir, object)` for on-demand repair.

Full reference: [docs/query-protocol/schema-mutations.md#rebuild-kf](../query-protocol/schema-mutations.md#rebuild-kf).

## add-index / remove-index locking fix

### Root cause

`add-index` and `remove-index` unlink and rebuild live index files in place (`.tg`/`.idx`/`.bm`) — the same destructive pattern `vacuum`/`truncate`/`reindex` use — but were classified under the shared per-object read lock (same class as `insert`) instead of the exclusive write lock those other rebuild commands correctly take. The btree cache keys entries by path string with no inode check, so a concurrent insert's on-the-fly index maintenance could land on the same path mid-rebuild and either have its write silently discarded (landing on the soon-to-be-unlinked old file) or corrupt the B-tree structure the rebuild was actively writing. Confirmed as the root cause of a production trigram-search bug where index files contained plausible byte volume but returned drastically undercounted results for common search terms — worse the longer the rebuild ran, since longer (multi-field) rebuilds give concurrent writers a bigger window to interleave.

### The fix

`add-index` and `remove-index` now take `objlock_wrlock` (exclusive), serializing them against all concurrent writes to the same object — identical to how `vacuum`/`truncate` already behave. See [Concepts → Concurrency](../concepts/concurrency.md#per-object-rwlock-objlock) and the [Lock model summary](../query-protocol/schema-mutations.md#lock-model-summary).

**Practical effect**: `add-index`/`remove-index` now queue behind in-flight writes and block new writes while running, rather than racing them. Rebuilding a large index under sustained write load will take noticeably longer to *start* (waiting for in-flight writes to drain) but is now guaranteed correct. Run large rebuilds in a maintenance window where possible.

## Fixes

- **`reindex_seg_cb` segfault on compacted objects** — the reindex segment scanner ignored `vlen` and read field values at a fixed offset, but compact (2026.06.4) writes records shorter than `ts->total_size` (trailing zero fields trimmed). Any `add-index`/`reindex` on a compacted object could read past the end of the record and segfault. Fixed with a per-worker zero-padded buffer used whenever `vlen < ts->total_size`.
- **`compact` dispatch double-dir path bug** — fixed a path-construction bug in the compact JSON dispatch that duplicated the directory segment.
- **`recover_one_stream` realloc leak on OOM** — a failed buffer grow during crash-recovery directory scanning leaked the prior allocation instead of freeing it (the `realloc()` return value overwrote the original pointer directly). Only triggers under OOM during crash recovery; fixed to match every other realloc call site in `slotcask.c`.
- **npm packaging** — `nql.c` was missing from `binding.gyp`'s source list, breaking NQL support in embedded/npm builds; added. npm package version corrected from an erroneous `1.1.2` back to sequential `1.0.7`.

## Upgrade notes

Recommended for all operators, **required** if you've run `vacuum`/compact on data ingested under 2026.06.4, or run `add-index`/`remove-index` under concurrent write load on any prior version:

```bash
./shard-db stop
./migrate          # runs rebuild-kf phase 2/3, then compact, then reindex as needed
./shard-db start
```

If any index built under concurrent writes on a prior version is suspect (e.g. search results look undercounted), force-rebuild it after upgrading:

```bash
./shard-db add-index <dir> <obj> <field> -f
```

Embedded (npm) consumers: rebuild the native addon (`npm run build:release` in `npm/`, or bump to the published `1.0.7+` package) — the fix lives in the C source compiled into the addon, not in JS.

Wire-compatible with 2026.06.4 — no client changes needed beyond the native addon rebuild above for embedded users.
