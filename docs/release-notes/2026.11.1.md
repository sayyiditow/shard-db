# shard-db 2026.11.1

2026.11.1 continues the R4 strict scalar grammars with the R5 packed-layout
work: the `layout=packed` token on an object's `schema.conf` line becomes the
authoritative object layout (a malformed token fails the load; there is no
legacy fallback), and the first start of this release migrates every object
to the packed layout before serving. Upgrading requires a **cleanly stopped
2026.10.2 root** — start 2026.10.2 against the DB_ROOT, stop it cleanly,
then upgrade; 2026.11.1 refuses an unclean root or a root with pending
commit markers and tells you so.

- Fixes: bitmap indexes could return missing rows after a recompose, and a forced single-field bitmap rebuild on a packed object produced an empty bitmap; both are fixed (bitmaps are rebuilt after every recompose and read packed cells). Bitmap indexes also stayed correct only until a keyfile shard grew or was compacted: every keyfile rebuild (in-place growth, `vacuum`) now renumbers the bitmap bits with the entries, crash-safely, so no `reindex` is needed after bulk loads; a startup repair rebuilds the indexes of an object whose rebuild was interrupted. `remove-field`/`rename-field`/`edit-field` no longer treat a `:removed` substring inside a default literal as a tombstone.
- `add-field`, `edit-field` and `vacuum compact` work on packed-layout (migrated or new) objects. See [schema-mutations](../query-protocol/schema-mutations.md) for the packed rules (rounding on numeric scale reduction, all-or-nothing validation, `seq` backfill order).
- **Packed layout is the default.** New objects are packed; the first start of this release migrates every existing object. `varchar` now reaches 4 MiB and `numeric` is an exact decimal (constrained `numeric:P,S` up to P=1000, or bare `numeric` with per-value scale). See [typed records](../concepts/typed-records.md).
- **Compatibility — `numeric:N` changes meaning for new objects.** It used to mean scale 2; for a *new* object `numeric:N` is now scale 0. Migration rewrites existing `numeric:N` to `numeric:N,2`, so stored values are unchanged.
- **Compatibility — display of whole values on migrated `numeric:N`.** A legacy scale-2 field rendered the whole value `100` as `100`; after migration it renders its declared scale, `100.00`. The numeric value is identical; clients that compare the text must normalise.
- **Compatibility — strict scalar grammars (R4), exact aggregates (R3), exact predicates/indexes (R2), complete ordinary writes/reads (R1).** Malformed `bool`/`date`/`time`/`uuid`/`ip`/`enum` input and decimals that do not fit are rejected instead of coerced; aggregates over decimals are exact. Details: [changelog](../reference/changelog.md).
- **Known issues.** The Node binding's async-handle lifetime concern recorded in R1 is unchanged. `JSON.parse()` on a response loses precision for wide decimals — see the npm README.
