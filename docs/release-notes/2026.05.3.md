# shard-db 2026.05.3

Operability + perf release. The headline is a reindex memory bomb fix — large multi-index schemas no longer freeze the host during `reindex` / `migrate`. B+ tree on-disk format bumps to v3 for O(1)-step DESC iteration; the `./migrate` upgrade path handles the rebuild transparently. A new env knob `INDEX_BUILD_BUDGET_MB` caps peak reindex memory.

Also bundled: the slotcask-engine work merged from branch — kf shard auto-resplit (no per-shard insert cap) and v2 default vacuum (seg compaction + streams self-heal).

No wire-protocol changes. **Existing index files are rebuilt by `./migrate`**; daemon refuses to open v1/v2 `.idx` files with a clear error pointing at `./migrate`.

## Highlights

### Reindex no longer OOMs hosts at scale

On a 25M-row × 12-indexed-field schema, prior `./shard-db reindex` peaked at ~25 GB resident — enough to freeze a 29 GB / 0-swap desktop in kernel direct-reclaim spin. Three independent fixes land together:

1. **Exact-size key buffers.** Scan callbacks used to `malloc(f->size)` per record per field — a `varchar:100` reserved 100 bytes for `"a@b.io"`. Now peeks the varchar length prefix and mallocs exactly what's needed.
2. **Pre-sized pair arrays.** `pairs[]` started at 4096 and doubled to live-count. Pre-size from `get_live_count()` with a 4096 floor and 1 Gi BtEntry cap; eliminates the 2× transient peak from realloc holding old + new buffers.
3. **Adaptive batching.** `cmd_add_indexes` no longer holds every field's `pairs[]` + `parted_per_field[]` alive simultaneously. The estimator computes per-field cost from `live_count × (BtEntry + partition copy + typed-key avg + glibc chunk overhead)` and groups fields into passes that fit `INDEX_BUILD_BUDGET_MB` (default 1024 MB). Each pass keeps the existing parallel scan + parallel build machinery; only the *fields-per-pass* concurrency is bounded. An oversized single field still runs alone via always-include-at-least-one.

The estimator knows per-type encoding (varchar 50 % fill, fixed types from the schema, composites by summing child ASCII widths) so `status+invoiceDate` is ~18 B per key, not a flat 64 B.

| 25M × 12 fields | Before | After |
|---|---|---|
| Peak RSS | ~25 GB | ~2 GB per pass |
| Wall time | Host froze; force-shutdown | **105 s** |
| Survives 29 GB / 0-swap | No | **Yes** |

**Tuning note:** `INDEX_BUILD_BUDGET_MB` is a *memory cap*, not a *speed knob*. At 25M × 12 fields: `1024 → 105 s`, `8192 → 92.7 s` — only ~13 % saved by 8× the budget. Per-record callback work scales `O(nfields × records)` regardless of batching; qsort + `btree_bulk_build` dominate. Raise for memory headroom (cgroup limits, swap-less hosts), not throughput.

### B+ tree v3 — O(1)-step DESC iteration

File magic bumped to `0x42545247` ("BTRG"). The header gains `last_leaf_page` (rightmost leaf in chain) and each leaf gains `prev_leaf` (backward link). DESC iterators start at `last_leaf_page` in O(1) and step left via `ph->prev_leaf`, replacing the old `root → leftmost → forward-walk → reverse-iterate` prologue and its malloc'd page-id array.

Split-path maintenance updates the back-links and bumps `last_leaf_page` when the rightmost leaf splits. `leaf_rebuild` preserves `prev_leaf` so vacuum-style rebuilds don't break the chain.

V1 ("BTRE", string-keyed) and V2 ("BTRF", no `prev_leaf`) magics are rejected at open. Run `./migrate` (which calls `reindex`) to rebuild. Operators upgrading from 2026.05.2 do nothing extra — the standard upgrade flow rebuilds indexes during phase 2.

### Parallel single-spec aggregate fast path

Sum/avg/min/max on an indexed numeric field with no criteria and no group_by used to walk the field's idx shards sequentially — at 25M × 16 idx shards that serialised 16 cold leaf scans for a 9-15 s total. Per-shard work now fans out via `parallel_for_io`; cold reads overlap on the I/O queue, then a reducer merges. Single-shard latency sets the floor instead of total work.

| 25M users, single-conn | 2026.05.2 | 2026.05.3 |
|---|---|---|
| `sum age` | ~9 s | **~190 ms** |
| `sum balance` | similar | similar |

(Run-to-run variance is high — these are warm-cache numbers. MIN/MAX already short-circuited after one leaf entry; they pick up the parallelism but the absolute savings are smaller.)

### kf shard auto-resplit — unbounded inserts

Each kf shard grows in place by doubling whenever its load crosses 75 %. No global ceiling; shards keep doubling indefinitely.

- **24-byte header** prefixes every kf file: `[magic 'SKF1'][version][total uint64][deleted uint64]`. `total` counts non-empty slots (live + tombstoned) — the resplit trigger metric. `deleted` counts tombstones; `live = total − deleted`.
- **Streaming resplit:** walk old kf in order, write each flag=1 entry directly into `kf.new`'s mmap'd region via linear-probe at the new capacity. Zero malloc — memory cost stays flat regardless of shard size. Tombstones are dropped during resplit, so resplit also reclaims tombstone space.
- **Crash safety:** `kf.new` is staged-then-renamed; old kf stays live until the atomic rename. `slotcask_open` unlinks leftover `kf.new` files at startup — idempotent recovery.

Closes the gap where the engine had a hard insert cap based on `splits × slots_per_shard`. The cap is gone; doubling is bounded only by disk space.

### v2 default vacuum — Direction-C seg compaction + streams-mismatch self-heal

Default `{"mode":"vacuum"}` on a v2 object used to be a no-op besides resetting the `deleted` counter. It now does two things:

1. **Direction-C seg compaction.** Per stream, every non-active seg file is stat'd for live count. The sparsest are pair-merged into denser ones — donor's live records migrate into recipient's tombstone holes, then the donor file is unlinked. The active seg of each stream is never touched, so concurrent appends after vacuum return are unaffected.
2. **Streams-mismatch self-heal.** If `slotcask_streams_for_nproc()` no longer matches `schema.streams` (CPU upgrade, container resize, hand-edited schema), the call promotes to a full rebuild that re-routes records into the new stream layout. `vacuum --splits=N` folds in the same check.

Response shape: `{"status":"vacuumed","cleaned":<files-dropped>}` for the light path; `{"status":"rebuilt", ...,"streams":N,...}` for the heavy path.

## Fixed

- **Pure-OR count missed single-child AND wrapper.** `criteria:[{"or":[...]}]` parses as `CNODE_AND { n_children=1, children[0] = or_node }` — the old guard classified that as hybrid and ran a per-record re-match it didn't need. Now returns `|KeySet|` directly.
- **Bench harness clobbered the operator's db.env.** `test_env_start_at` (every C bench's persistent mode) wrote a fresh minimal `db.env` over `<base>/db.env`. With `SHARD_BENCH_DB_ROOT=./db`, base resolved to `.` so it silently nuked the repo-root config. Now skips the write when an env file is present and parses the existing `PORT=` so the bench client connects to where the daemon actually binds.

## Upgrade

The btree on-disk format change means `.idx` files must be rebuilt. `./migrate`'s phase 2 already runs `reindex` and handles this transparently — the standard upgrade flow is unchanged:

```bash
./shard-db stop
# replace build/bin/ contents with new release tarball
./migrate                   # rebuilds btree indexes to v3
./shard-db start
```

`./migrate` is idempotent; safe to re-run. The reindex pass now respects `INDEX_BUILD_BUDGET_MB` per object, so the upgrade itself is bounded — no more freezing hosts on a multi-million-row tenant.

### What happens if you skip `./migrate`

The daemon starts but every btree open fails with:

```
btree: rejecting V2 (no prev_leaf) format at <path>/indexes/<field>/<NNN>.idx — run ./shard-db reindex (or ./migrate)
```

Run `./migrate` (or `./shard-db reindex` on a started daemon) and you're back in business. No data loss — only indexes are rebuilt, source records are untouched.
