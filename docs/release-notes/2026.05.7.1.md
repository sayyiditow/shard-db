# shard-db 2026.05.7.1

Patch release on the 2026.05.7 line. Headline fix is a **correctness bug in `cmd_find`** that returned `[]` non-deterministically on indexed queries served by a busy daemon. Bundled with that: **edit-field polish** (default carry-through, smart reindex, dry_run), **add-field computed defaults** (backfill existing records on `:default=seq/uuid/random/literal`), and **startup warmup** (the daemon pre-touches every kf + index file's first page on start so the first user query doesn't pay cold disk I/O).

No `./migrate` required. No wire-format changes. Drop in the new binary and restart.

## Bug fixes

### `find` was dropping output on reused pool workers (#64)

Pre-fix, `find` queries served from a daemon that had already handled traffic intermittently returned `[]` even when records matched. The two callbacks driving the find fast paths — `stream_find_cb` (limit ≤ 1000) and `cursor_find_cb` (any `order_by`) — were writing to a `__thread FILE *g_out` that retained a stale FILE* from a previous request. The guard `if (!g_out) g_out = sc->parent_out;` only fired on a worker's first invocation; subsequent reuse skipped the assignment and OUT() wrote to a closed fd.

Symptoms surfaced via the HN explorer: queries like

```json
{"mode":"find","dir":"hn","object":"comments",
 "criteria":[{"field":"story_root","op":"eq","value":"868109"}],
 "limit":50}
```

returned `[]` even though `count` reported 239 matches. Non-deterministic across runs because a fresh worker still worked correctly. Fixed by forcing `g_out = sc->parent_out` unconditionally at every callback entry. `CursorFindCtx` gains a `parent_out` field (was relying entirely on whatever the worker had stashed).

### `FT_TIMESTAMP` was silently compared against zero (#64)

`compile_one` in `query.c` has a `switch(cc->ftype)` that parses each criterion's value into `cc->i1` per typed kind. Every type had a case **except FT_TIMESTAMP** (added in 2026.05.6). `cc->i1` stayed at the memset-zero default, so every timestamp criterion silently compared against 0:

| Op | Effective match | Symptom |
|---|---|---|
| `time eq X` | `eq 0` | 0 rows |
| `time gte X` | `gte 0` | ALL rows (filter silently ignored) |
| `time lt X` | `lt 0` | 0 rows |
| AND-intersect with timestamp sibling | sibling → `lt 0` | intersect collapses to 0 |

`count` was unaffected because it goes through `encode_criterion_value` (config.c) which DID handle FT_TIMESTAMP. Anything that runs `criteria_match_tree` (find, aggregate post-filter, AND-intersect) was wrong. Fixed by adding `case FT_TIMESTAMP:` next to `case FT_LONG:` in both the scalar and IN-list switches (same int64 BE encoding).

## Features

### `edit-field` polish bundle (#65)

Three followups from the 2026.05.5–.7 cycle land together:

- **Default-modifier carry-through.** When an `edit-field` spec OMITS `:default=…` / `:auto_create` / `:auto_update`, the modifier from the OLD `fields.conf` line is preserved. `edit-field age:long` against an existing `age:int:default=42` keeps the default instead of silently wiping it. The helper refuses to write a truncated suffix when it wouldn't fit (returns 0 instead of half-modifier corruption).
- **Smart reindex.** `cmd_edit_fields` now tracks per-edit dirty flags (`field_needs_transform`) and rebuilds only indexes whose referenced fields actually changed encoding. Response carries both `indexes_rebuilt` and `indexes_skipped`. No-op edits (default-modifier-only) return `"rebuilt":false` and skip every index.
- **`dry_run` flag.** `"dry_run":true` runs full validation + cross-type refusal + per-record pre-flight scan, then returns `{"status":"ok","dry_run":true,"fields":N,"would_rebuild":bool}` without writing anything.

### `add-field` computed-defaults backfill + parser fix (#67)

Pre-fix, `add-field` rejected `:default=<literal>` and `:default=seq(…)` outright (the parser only matched bare type tokens — anything with a trailing modifier hit FT_NONE), and even when a `varchar:N:default=uuid()` spec happened to slip through, no backfill ran — existing records got zeroed bytes for the new field.

The fix has three parts:

1. **Parser accepts modifier-bearing specs** on both `add-field` and `edit-field`. Extracted a shared `parse_default_modifier` helper that strips the trailing modifier into `tf->default_kind` + `tf->default_val` and hands the cleaned type spec to `parse_field_type`. Closes the previously-documented "no way to change a default via `edit-field`" gap from #65.
2. **Backfill during the rebuild walk.** For each new field with a computed default:
   - `:default=<literal>` — stamped on every existing record.
   - `:default=seq(<name>)` — server reserves a contiguous range via `seq_next_val_batch` before the rebuild, assigns sequentially per record.
   - `:default=uuid()` — fresh UUIDv4 per record.
   - `:default=random(N)` — fresh `getrandom` bytes per record. Validation rejects `N > field_size` pre-rebuild.
   - `:auto_create` / `:auto_update` — inert during backfill (they only fire at insert/update; not retroactive).
3. **Latent slot-write bug fixed.** When the new field happened to fit within 8-byte slot-size padding, `slot_changed` was 0 and the rebuild walk took the verbatim re-insert path that wrote only the OLD value length — the new field bytes were silently never written. Now `slot_changed = (size changed) || (n_added > 0)`. Existing `add-field` benches in the slot-padding regime were measuring "add-field that silently skipped writing the new field"; re-bench.

### Startup warmup (#68)

Cold daemon start used to load every cache lazily — first query after restart paid disk-read time for every (kf, index) file it touched. On a populated dataset (789K-row HN comments) the explorer homepage took ~15 s after a daemon restart.

New env knob `WARMUP=` (db.env):

- **`async`** (default) — daemon accepts connections immediately, a detached thread walks every `(dir, object)` and touches each `.kf` / `.idx` / `.bm` / `.tg` file (open + `posix_fadvise(WILLNEED)` on Linux + read first page) to populate the OS page cache. First queries racing the warmup still pay cold cost for what hasn't been reached yet, but total wall-clock-to-warm drops drastically.
- **`sync`** — block startup until warmup completes. Restart blocks the listening socket for the full warmup time. Use for "warm before serving" production posture.
- **`off`** — no warmup. Lazy cold reads as before.

Stream segment files (`.dat` under `data/streams/`) are deliberately NOT warmed — they can be GBs each on populated objects and warming them all would evict the smaller, hotter index pages from the page cache.

Live verification on the HN dataset (4 objects, 416 kf + 1024 index files): 35 ms warm. Cold time depends on disk + RAM, but in `async` mode happens off the critical path.

## Compatibility

- Wire format: unchanged.
- On-disk format: unchanged.
- No `./migrate` step required.
- Linux x86_64, Linux arm64, macOS arm64.

## Upgrade

```bash
# Replace build/bin/ contents with the new release artifacts
# (shard-db + shard-cli + migrate). No further steps.
./shard-db stop
cp shard-db /opt/shard-db/bin/    # or wherever you deploy
./shard-db start
```

`WARMUP=async` is the new default — restart picks up the warmup automatically. To preserve pre-2026.05.7.1 behavior set `WARMUP=off` in db.env.
