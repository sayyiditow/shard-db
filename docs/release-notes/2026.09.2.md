# shard-db 2026.09.2

This release widens calendar `datetime` storage from 6 to 7 bytes and adds a
startup migration that rewrites existing 6-byte objects. It also ships the
explicit, type-correct aggregate handling previewed in the changelog.
The npm binding is released as version `1.0.21`.

## Upgrade requirements

Upgrade only from a database root stamped `2026.08.2` or `2026.09.1`; older
roots are refused. Stop writes and let the previous release finish recovery
before replacing the binary.

The first 2026.09.2 start migrates every populated root with
`2026.08.2 ≤ .version < 2026.09.2`: each object storing calendar `datetime`
fields is rebuilt in place to the 7-byte layout, its datetime indexes are
rebuilt, and the root is stamped `2026.09.2` only after every object
migrated. The migration is crash-safe (it runs inside the same rebuild
transaction protocol as `edit-field`, rolling back cleanly on any failure)
and idempotent (a `#datetime_7byte` marker in each object's `fields.conf`
skips objects that already migrated, so an interrupted upgrade resumes
safely). Leave the data directory untouched while a migration start is in
progress.

**Upgrade window:** the release after 2026.09.2 raises the minimum supported
source version to `2026.09.2` and refuses roots that have not been migrated.
Pass through 2026.09.2 first — do not skip it when jumping multiple
releases.

## Highlights

- `datetime` records are 7 bytes (`yyyyMMdd` int32 BE + 3-byte BE
  seconds-of-day), fixing a silent wrap present since the type was
  introduced: the old 2-byte time field truncated evening times
  (`18:12:16`–`23:59:59`) to early-morning values on insert, read, indexes,
  criteria, ordering, and aggregate output. The full day now round-trips
  exactly. The wire format is unchanged (`yyyyMMddHHmmss`), and `datetimems`
  is untouched.
- Already-truncated historic values keep their stored (wrapped) meaning
  after migration — the migration preserves what the old bytes represent;
  it cannot restore seconds lost before the upgrade.
- A populated `2026.08.2` root previously took the accept-without-rewrite
  fast path at startup; it now migrates like any other old root.
- Aggregate type handling is explicit and type-correct: zero-valued numeric
  fields participate in aggregates with real `0` group keys, varchar and
  calendar `min`/`max` return textual values, and unsupported combinations
  return structured errors. This is a wire-visible change for clients that
  depended on the former numeric-zero fallbacks.

## Compatibility

The wire protocol remains compatible; datetime values are exchanged as the
same 14-digit `yyyyMMddHHmmss` strings as before. The on-disk record layout
for `datetime` objects changes, which is why the startup migration is
mandatory and gated on the root version. Clients reading `datetime` values
see evening times as the true stored strings for the first time — any client
that learned the wrapped values as canonical (e.g. cached
`20240102054743` for an original `23:59:59` insert) must be re-checked;
pre-migration inserts remain wrapped, only values written after the
migrated binary is running carry full precision.

## Validation

New regression coverage: `test-datetime-evening` (full-day round-trip,
index, criteria, and ordering across the legacy `18:12:15` boundary),
`test-version-gate` (the full `shard_db_version_decide` decision matrix
including the new MIGRATE band), and `test-datetime-migration` (an
old-layout 6-byte fixture migrated end-to-end at startup, with restart
idempotency and a non-datetime control object).
