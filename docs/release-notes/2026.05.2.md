# shard-db 2026.05.2

Performance release. Aggregate fast paths land for `sum / avg / min / max / count`, regex starts using indexed btrees, the planner gets four cleanups, the bench harness gains a unified table view, and a startup-validator papercut from 2026.05.1 is fixed.

No schema changes. No wire-protocol breaking changes. Drop-in replacement for 2026.05.1 binaries.

## Highlights

### Aggregate is up to 43× faster

Single-spec aggregates without group_by / having / criteria on an indexed non-varchar field now walk btree leaves directly. Encoded leaf bytes decode straight to a double, so no record fetch and no slot-header probe per row.

| Bench row (1M users) | 2026.05.1 | 2026.05.2 |
|---|---|---|
| AGGREGATE single-fn standalone (30 rows total) | 8.8 s | **202 ms** (~43×) |
| `min/max` per type (each row) | 200–400 ms | **0.04–0.35 ms** |
| `sum/avg` per type (each row) | 250–380 ms | **13–22 ms** |
| `agg(count where field neq X)` | 156 ms | **0.42 ms** (~370×) |
| `count(EXISTS field)` non-varchar | 22 ms | **0.05 ms** (no scan; live_count) |

Multi-spec aggregates and group_by paths are unchanged — they need every record decoded.

### Regex on indexed varchar

`regex` and `not_regex` on indexed varchar fields no longer fall to a full record scan. The planner allows them through `leaf_is_indexed` and the callback runs `regexec` against the literal leaf bytes. A thread-local `(pattern → regex_t)` cache fires `regcomp` once per thread per distinct pattern instead of once per leaf entry. Non-varchar indexed fields stay full-scan because their leaves carry encoded sortable bytes.

### Query planner cleanups

- **Range coalesce on same-field bounds** — `gt/lt/gte/lte` pairs on the same field collapse to one `BETWEEN` with `min_exclusive`/`max_exclusive` flags. All four pairings (`gt+lt`, `gt+lte`, `gte+lt`, `gte+lte`) hit the indexed range path.
- **OR limit pushdown** — pure-OR `find` paths stop building the union once `offset+limit` candidates are reached.
- **KeySet capacity floor on intersect** — capacity is now `max(leaf_capacity_hint, live_count)`. The 3-way `active+age+score` intersect on bench-queries went from **74 s → 91 ms** (~800×) once the capacity stopped capping early.
- **Index fan-out curve** — `index_splits_for(splits)` is now a non-linear table (`8→2, 16→4, 32→4, 64→8, 128→16, 256→16, 512→32, 1024→64, 2048→64, 4096→128`) instead of `splits/4`.

### Fixed — `count(varchar field)` over-counted empty strings

`agg_scan_cb`'s `AGG_COUNT` branch incremented for every matched record without checking the field's value. Typed records always carry every field, but a varchar field can have empty content (`elen == 0`); `count(varchar_field)` should match `OP_EXISTS`-on-varchar semantics and skip empties. Test `test-count-varchar-field` covers count(*), count(int), count(varchar), criteria-narrowed and grouped forms.

### Fixed — `./shard-db start` reported success but daemon didn't listen

The startup metadata validator added in 2026.05.2-rc ran *after* `fork()`, so its stderr went to `/dev/null` and the parent had already printed `shard-db started (pid N)`. Operators saw "started" then immediate "stopped" with the only diagnostic in `error.log`. Two fixes:

1. Validation moved before fork so any future fatal error reaches the user's terminal.
2. The `dirs.conf` consistency rule softened from fatal to a warning. Stale schema entries can't cause silent mis-routing — the auth/route layer already rejects unknown tenants — so refusing startup blocked operators on any DB that had outlived a removed test tenant.

### Tooling — bench harness unified table view

All eight benches (`bench-queries`, `bench-invoice`, `bench-joins`, `bench-kv`, `bench-kv-parallel`, `bench-parallel`, `bench-grow`, `bench-incremental`) now produce sectioned tables with relative bar charts and min/p50/max/total footers. Pre-computed timings (bulk-insert throughput, pipelined latency batches, parallel-worker fan-out) share the same section as single-shot query rows; an optional trailing column carries throughput-style metadata (`0.39 M rows/s`, `p50=31µs  31 k op/s`).

### Tooling — `bench-queries` covers every operator × every applicable type

222 rows across 21 sections. Every operator class touches every applicable field type so per-type pathology surfaces in one run: eq / neq / range / `in`/`not_in` / `exists` / string ops (CS + CI) / `len_*` / regex / field-vs-field / OR widths / aggregate single-fn + with-criteria + bundled / cursor by 7 indexed types.

### Security — Coverity + CodeQL clean

All Coverity defects (97 total) eliminated: 71 fixed, 26 dismissed, **0 outstanding**, 0.00 defect density. Specifically this release closes:

- TOCTOU stat→opendir patterns (`validate_metadata`, restore-path index walk, restore-path empty-subdir check, fields.conf comparison).
- TOCTOU stat→fopen on fields.conf comparison — replaced with open-then-fstat.
- `LOCK_EVASION` on `slots_per_shard` — explicit `atomic_load_explicit` so Coverity recognizes the C11 atomic semantics (the field is already `_Atomic`, the bare-field read was already atomic, but the checker didn't see it).
- Resource leak in `validate_metadata` early-return.
- Dead code in `auto_vacuum` `pct_observed` ternary.
- Unchecked `fread` return in `parse_object_meta`.
- Two `snprintf` overflow patterns in test fixtures (CodeQL CWE-122) — switched to the existing `SB_APPEND` macro.

## Upgrade

This release is wire-compatible with 2026.05.1. Replace the binaries:

```bash
./shard-db stop
# replace build/bin/ contents with new release tarball
./migrate                   # idempotent; safe to re-run
./shard-db start
```

`./migrate` for 2026.05.2 is a no-op — schema, on-disk layout, and the per-shard btree index format are unchanged. The binary is bundled so future migrations have a single entry point.

## Deferred to 2026.05.3

- macOS port (epoll → kqueue, memfd → tmpfile, posix_fallocate → ftruncate; CI matrix expansion).
- `edit-field` (same-type rename + width adjust; cross-type changes refused).
- Computed defaults on `add-field` (backfill-only for field-derived expressions).
