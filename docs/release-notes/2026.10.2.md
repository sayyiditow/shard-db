# shard-db 2026.10.2

This release makes typed fields truly nullable: every record carries a
per-record null bitmap, explicit JSON `null` stores NULL, and the SQL
`NOT NULL` constraint arrives as the `:not_null` field modifier. It also
ships conditional writes — atomic computed updates (`$incr` / `$copy`),
object-scope guards (`if_match` / `if_no_match`), the full filter-tree
grammar in write `if` conditions, and opt-in `return_record`. Indexed
fields gain a NULL tier via the new `'BTRI'` B+ tree format, installed
by a startup migration on first open. The npm binding is released as
version `1.3.0`; the minimum prior binding for a direct upgrade is
`1.0.22` — older prebuilds embed pre-`2026.09.2` engines whose roots
are refused by the eligibility gate, so open once with `1.0.22` or
later (e.g. the current `1.2.0`) before upgrading.

## Upgrade requirements

The eligibility gate is unchanged from 2026.10.1: a populated root must
carry clean-open evidence at or after `2026.09.2` — such roots open
as-is and re-stamp; older roots refuse with an upgrade hint (install
2026.09.2, start it once against the DB_ROOT, then upgrade). A
filesystem-empty root initializes directly. The minimum supported
source release stays `2026.09.2`.

The first 2026.10.2 start migrates every indexed object to the
`'BTRI'` index format: each object is reindexed through a strict
durability-checked entry point (an unconfirmed publication fails the
start; a partially published shard retries whole on the next attempt),
any pending KFM2 commit-intent markers are replayed against the rebuilt
indexes, and completion is durably stamped (`.btri-migrated` at the
DB_ROOT) before the daemon serves. The migration is forward-only — a
crash at any point replays to completion, never rolls back — and
subsequent starts skip it. No operator action is required; leave the
data directory untouched while a migration start is in progress.

Before an older root is reinterpreted, a read-only startup audit
refuses roots whose pre-2026.10.2 `fields.conf` files contain the
reserved `not_null`/`nullable` substrings on a non-comment field line
(an old enum value or default literal spelled like the new grammar is
ambiguous). Resolve it with the previous release's supported schema
edits — change the default literal, or rename the enum value with
explicit `allow_rename` (which preserves stored value positions); do
not delete columns or hand-stamp the root. The audit never edits schema
bytes; a clean older root opens and stamps normally.

## Highlights

- **Real NULL for typed fields.** Every record carries a null bitmap
  (`1 + ceil(nfields/8)` bytes at the head of the value region).
  Explicit JSON `null` stores NULL and wins over `:default=`; an
  omitted insert field with no default is NULL; update semantics are
  explicit-null-clears / omitted-carries-forward. Reads render NULL as
  bare JSON `null` (CSV: empty cell); legacy records stay
  byte-identical until a rewrite converts them
  rendering-preservingly. Raw unquoted JSON `null` operands are
  rejected by the criteria parser; quoted `"null"` stays a string.
- **Criteria NULL semantics.** Value predicates never match NULL and
  their negations don't either — the count/aggregate complement
  optimizations (live-minus-positive, NEQ split) were removed because a
  NULL belongs to neither side. `exists`/`not_exists` test nullness
  with per-record, generation-correct semantics so indexed and
  unindexed results agree on mixed-generation data.
- **`:not_null` constraint.** `name:type[:...][:not_null|:nullable]` —
  on a constrained field every NULL-producing write branch is a request
  error, including malformed `uuid`/`ipv4`/`ipv6` sentinels. Single
  writes and criteria-form bulk update reject the whole request
  (`field '<name>' is not nullable`); per-record JSON bulk
  insert/update skip and count the violating record while peers commit.
  Well-formed zeros (`0.0.0.0`, `::`, nil UUID, `0`, `""`) stay legal.
  Adding `:not_null` to existing data first runs a read-only, strict,
  fail-closed scan — nonzero NULLs refuse the edit with a count. The
  constraint adds no on-disk format change and rides the null bitmap.
- **NULL-aware aggregates.** `sum`/`avg`/`min`/`max` skip NULLs, `avg`
  of all-NULL renders `null`, `count(field)` counts non-NULL, and
  `group_by` gives NULL its own bucket rendered as bare JSON `null` —
  `NULL`, `""`, and the literal `"null"` are three distinct buckets,
  with indexed and scan paths byte-identical. Bitmap-indexed fields
  keep their documented gap: NULL groups and exists/not_exists on
  bitmap-indexed fields fall back to full scans.
- **`'BTRI'` index format with a NULL tier.** B+ tree magic rolls
  `'BTRH'` → `'BTRI'` (`BT_MAX_VAL_LEN` 512 → 544): indexed fields
  store one key per record including NULLs — value keys
  `[0x00][sortable bytes]`, NULL keys `[0x01]` — so ranges stop below
  the NULL tier, ordered finds place NULL rows last ASC / first DESC,
  and keyset cursor tokens carry a per-field tier array that crosses
  the NULL boundary without repeating or skipping rows. A `'BTRH'`
  file also refuses per-request as defense-in-depth.
- **Conditional writes** (no on-disk format change, no index change,
  no migration; all wire changes are additive):
  - **Computed updates** on single `update`: a value field may hold
    `{"$incr": <literal>}` (checked add — overflow rejects the whole
    request and leaves the record untouched) or `{"$copy": "<field>"}`
    (same-type copy; NULL source/destination rejects). In per-record
    bulk-update, a record whose computed span fails validation skips
    while peers commit.
  - **Object-scope guards** `if_match` / `if_no_match` on
    insert/update/delete: unlike key-scoped `if`, guards check *other*
    records in the same object atomically with the write (the written
    record is excluded by exact key bytes) — enabling unique-rows and
    requires-a-parent constraints. Single-write only; mutually
    exclusive; fail-closed on every error path. Guarded writes hold
    the object's shared lock and reserve its per-shard writer gates
    through the check — readers continue, other writers wait.
  - **`if` filter trees**: write conditions accept the full read
    grammar — nested `{and}/{or}` trees (depth ≤ 16), not just flat
    AND arrays. Comparisons are typed (matching `find`), unknown
    fields and invalid regex patterns reject with
    `invalid if condition` instead of silently never-matching, and
    `if: []` keeps its vacuous pass.
  - **`return_record`** opt-in on insert/update/delete: the success
    response carries the committed record (defaults, auto_create/
    auto_update and computed values applied) or the removed record
    (delete). Without the flag all responses are byte-identical to
    previous releases.

## Compatibility

Wire changes for readers of nullable data are intentional: typed fields
that previously rendered as `""`/`0`/"null"-string sentinels now render
bare `null`, and `count`/`aggregate` results change by design where a
NULL belongs to neither side of a predicate. Clients that treated the
old sentinels as canonical values must be re-checked. The single-write
CAS surface grows additively — responses without the new options are
byte-identical to previous releases. On disk, typed records gain the
null bitmap (legacy v2 records convert on rewrite, never in place) and
B+ tree files change format (installed by the startup migration above);
kf shards, segment files, and the KFM2 marker format are unchanged.
