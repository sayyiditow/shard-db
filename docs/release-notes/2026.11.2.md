# shard-db 2026.11.2

2026.11.2 fixes a proven data-loss bug in the segment-scan tail heuristic shared by
startup recovery, vacuum and the O_DIRECT reindex/vacuum scanner. It is a
correctness/containment release: no on-disk format change, no wire or CLI change, and
no schema or configuration change.

- **The bug.** Every mutation writes its record bytes with flag=0 (the durable "P"
  phase) before the KFM2 commit marker and activation. A write whose window dies
  between P and activation leaves a structurally valid flag=0 record with intact
  content — an inert "grave". Repeated over months of dev churn (and any pre-marker
  I/O failure), long grave runs defeat the scans' bounded one-`slot_size` resync
  window: startup recovery parked the append frontier at the first grave run, so
  later appends overwrote live records beyond it (dangling live keyfile entries; the
  2026.11.x layout migration refuses such an object with `invalid live kf
  references`), vacuum dropped or under-migrated segments whose live records sat
  behind graves, and reindex missed records. Confirmed on real incident data and by
  the regression tests below.
- **The fix.** All four scans (startup `recover_one_stream`, vacuum's
  `seg_stat_one_varlen`, the compaction recipient free-list walk, and
  `seg_scan_o_direct`) now step over hash-verified staged records by their declared
  size — every grave is hash-verified before it is stepped over or harvested; a
  failed hash is a desync, never a blind step — and break as "unwritten tail" only
  after a hole-aware full-remainder search finds no hash-valid record ahead. The
  search asks the filesystem for data extents (`SEEK_DATA`/`SEEK_HOLE`, trusted via a
  per-filesystem runtime probe) and reads them with `pread`, never through the
  mapping. Vacuum now also harvests verified grave capacity in its recipient free
  list, so it reclaims grave space and neither starves nor drops such segments.
- **Two adjacent fixes found by the end-to-end review.** Vacuum's free pool now drops
  slots consumed by compaction (a rebuilt-from-tombstones pool slot the migration
  consumed could be handed to a later insert, overwriting a migrated record), and
  `backup`/`restore`'s file copy preserves sparseness (a dense copy made every open
  pay the full rolling resync scan: ~155 ms per 8-stream object vs ~3.8–4.2 ms
  sparse, measured warm-cache).
- **Operator signal.** At open, each stream whose active segment holds staged,
  not-activated records logs one WARN line (they are skipped as dead space; vacuum
  reclaims the inert ones once the segment rotates). If you see it, run `vacuum` on
  the object when convenient.
- **Known cost.** On a sparse-aware filesystem a healthy open adds ~4 ms per
  8-stream object (vs ~0.2 ms before): one bounded search plus one open and an
  extent query per stream. On filesystems without a usable `SEEK_DATA` — or on
  fully-allocated/plain-copied segments (backups restored by earlier releases, plain
  `cp` copies) — the fallback rolling scan costs ~one full-segment `pread` per stream
  per open (~155 ms per 8-stream object, measured) until the data is re-copied
  sparsely (e.g. by a `backup`+`restore` pair with this release).
- **`invalid live kf references` (the layout-migration refusal).** Roots written by
  2026.10.2 or earlier may already carry the damage this release prevents; 2026.11.2
  does not repair existing damage. See
  [deployment](../operations/deployment.md#refused-invalid-live-kf-references) for
  what the refusal means and what to do today (restore the affected object from a
  pre-upgrade backup or re-ingest). No repair command ships in this release.
- **Compatibility.** No on-disk format change; wire-compatible; no CLI/config change.
  Opening a root under 2026.11.2 re-stamps `$DB_ROOT/.version`, after which
  **2026.11.1 and npm binding 1.4.0 refuse it** (downgrade barrier) — plan the
  upgrade one-way. Roots written by 2026.11.1 open normally.
- **npm binding `1.5.0`** embeds this engine. The minimum prior binding for a direct
  upgrade is `1.4.0` (it embeds `2026.11.1`); open once with it and close cleanly
  first.
- Regression tests: `test-slotcask-grave-run-frontier` (10 scenarios: incident shape,
  interior/tail grave runs, gap-then-grave compound, far island behind a hole,
  hash-failed grave, sparse-tail no-materialization guard, hole-punched spanning
  record, wide-resync fail-closed), `test-slotcask-vacuum-grave-run` (vacuum
  preserves records behind graves; recipient grave harvest pin),
  `test-od-scan-healthy-tail` (healthy-tail read bound, record behind a hole,
  grave-larger-than-chunk livelock proof, extent-larger-than-buffer overlap rule,
  grave at EOF, hole-punched spanning record), `test-slotcask-compact-pool-consumed`
  (pool slots consumed by compaction), `test-backup-copy-sparse` (sparse-preserving
  backup copy). Plan:
